# Get Freak

An 18+ mobile app of games for couples, played together on one phone.

## Stack

Expo, React Native, TypeScript, Expo Router and NativeWind. Node 26 and pnpm. No backend. Native modules: `expo-sqlite` (SQLCipher build) for storage, `expo-secure-store` and `expo-crypto` for the key to the encrypted store, `expo-audio` for button sounds and `expo-haptics` for vibration feedback.

## Layout

- `apps/mobile`: the Expo app. Its button sounds are in `assets/sounds`, made by `scripts/generateSounds.mjs`.
- `packages/core`: game rules in pure TypeScript, with no React, React Native or Expo imports.
- `packages/content`: user-facing copy and other data.
- `packages/tokens`: design tokens: colours for the light and dark themes, type, spacing and radius.
- `tools`: data shared by the checks, such as the pattern that finds raw colour values.
- `docs/architecture.md`: how the code is laid out and why.
- `docs/runbooks/error-monitoring.md`: setting up Sentry, sending a test error and reading a report.

## Setup

1. Use Node 26: `nvm use` reads `.nvmrc`.
2. Install dependencies from the repository root: `pnpm install`.
3. Create a development build, which the app needs because it uses a development client:
   - iOS simulator or device: `pnpm --filter @getfreak/mobile ios`
   - Android emulator or device: `pnpm --filter @getfreak/mobile android`
4. Start Metro: `pnpm --filter @getfreak/mobile start`. Open the development build and it
   connects to Metro.

Building for iOS needs Xcode, and building for Android needs the Android SDK. The `ios` and
`android` folders are generated by the build and are not committed.

## Installing on a phone

Builds for a phone are made by EAS Build, Expo's cloud build service, so no Android SDK or Xcode is
needed on your machine. The profiles are in `apps/mobile/eas.json`. Both pin Node and pnpm to the
versions this repository uses.

- `preview`: a release build of the app as an Android `.apk`, with the JavaScript bundled inside.
  It runs on its own, with no computer nearby. Use this to play.
- `development`: the development client as an `.apk`. It needs Metro running on your machine
  (`pnpm --filter @getfreak/mobile start`) and on the same network.
- `production`: the store build. It makes an Android app bundle (`.aab`) for Google Play and an
  iPhone build for the App Store, with a build number that rises on every build, and it listens to
  the `production` update channel. It cannot be installed straight onto a phone, so use `preview`
  to play. Store builds need the developer accounts and app records from FRK-52, and iPhone builds
  need the paid Apple Developer Program. The store submission settings in `eas.json` name two key
  files, which the owner keeps outside git in `apps/mobile/secrets/`: the Apple API key
  (`apple-api-key.p8`) and the Google service account key (`google-service-account.json`). Git
  ignores that folder and every `.p8` file. A build made after a native config change needs a fresh
  install, because the change alters the native fingerprint.

To make an Android build, from `apps/mobile`:

1. Sign in once: `npx eas-cli@latest login`.
2. Build: `npx eas-cli@latest build --platform android --profile preview`.
3. When it finishes, open the link it prints on your phone, download the `.apk` and install it.
   Android asks you to allow installs from your browser the first time.

Installing a newer `.apk` over the old one keeps what the app has stored on the phone.

Adding or changing a native module, such as `expo-audio` or `expo-haptics`, needs a new build. A
development client made before the change does not have the module, so make a new one.

## Publishing an update

Once a phone has a build made with `expo-updates`, JavaScript and content changes reach it without a
new build. The `preview` build listens to the `preview` channel. From `apps/mobile`:

```
EXPO_PUBLIC_COMMIT_SHA=$(git rev-parse HEAD) npx eas-cli update --channel preview --environment preview --message "What changed"
```

`--environment preview` gives the update the preview environment's variables, such as the Sentry
DSN, and the commit names the release on an error report.

After publishing, upload the update's source maps so its error reports show readable stacks. This
needs `SENTRY_AUTH_TOKEN` in your shell, and the update still works without it:

```
pnpm exec sentry-expo-upload-sourcemaps dist
```

The app checks at launch and downloads the update in the background. It runs from the next time the
app is opened from closed, never in the middle of a round, and a short toast says it has updated.
CI never publishes.

An update only reaches builds whose native fingerprint matches. The fingerprint is the runtime
version, and it is computed automatically from the native parts of the project, so a new native
module, plugin, permission or native config changes it with no extra step. Anything native needs a
new build. The first build with updates in it has to be installed by hand, and every update after
that arrives over the air.

Publish from a checkout with the same lockfile and config as the build. If they differ, the
fingerprint differs and the update simply does not reach the phone, which fails safe. To print the
current value, from `apps/mobile`:

```
env -u NODE_PATH node node_modules/expo-updates/bin/cli.js fingerprint:generate --platform android
```

iPhone builds are made only by the `production` profile, and need the paid Apple Developer Program
(see above).

## Everyday commands

Run these from the repository root.

| Command          | What it does                                  |
| ---------------- | --------------------------------------------- |
| `pnpm lint`      | ESLint, then a Prettier check                 |
| `pnpm typecheck` | `tsc --noEmit` in every package               |
| `pnpm test`      | Jest in every package                         |
| `pnpm check`     | `lint`, `typecheck` and `test`, in that order |
| `pnpm format`    | Writes Prettier fixes                         |

To run one package's tests, filter by package name, for example
`pnpm --filter @getfreak/core test`. Jest options go after the script name, for example
`pnpm --filter @getfreak/mobile test --watch`.

## Continuous integration

GitHub Actions runs on every pull request, on every push to `main`, and on demand.

- `scope` works out which packages the change affects, using pnpm's dependency graph: the changed
  packages plus the packages that depend on them. A change outside `apps/` and `packages/`, such as
  root config, the lockfile or the workflows, runs everything.
- `lint` runs ESLint and the Prettier check on every change.
- `core`, `content`, `tokens` and `mobile` each run `typecheck` and `test` for that package, and are
  skipped when the change cannot affect them.
- `release-bundle` runs only on a full run started by hand. It bundles the Android release the way
  Gradle does, with the Expo CLI under plain `node` and without pnpm's shim, so a package that
  `apps/mobile` uses but does not declare fails here.
- `checks` is the one required status. It fails if any job failed or was cancelled, and passes when
  every job passed or was skipped. Branch protection names only `checks`.

To start a full run by hand, open the Actions tab, choose the CI workflow, then Run workflow. Or run
`gh workflow run CI --ref <branch>`.

`pnpm check` is the local equivalent. It runs `lint`, `typecheck` and `test` for every package.
