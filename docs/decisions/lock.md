# App lock

- **Off by default** (FRK-53, tech lead 2026-11-19): A player turns the lock on in Settings. Nothing asks at first launch.
- **A 4 digit PIN is required, biometrics are an extra** (FRK-53, tech lead 2026-11-19): Face ID, Touch ID or the phone's fingerprint or face unlock sit on top of the PIN and never replace it. They are offered only when the phone has them set up.
- **The PIN is a salted SHA-256 hash in secure storage** (FRK-53, tech lead 2026-11-19): Readable only while the phone is unlocked and only on this device. It is never in the key-value store and never logged. Whether the lock is on is read from the presence of the hash, so the two cannot disagree.
- **When it locks** (FRK-53, tech lead 2026-11-19): On every cold start, and after 60 seconds or more in the background. The iOS `inactive` state (the notification shade, Control Center, a call banner) and quick trips do not count. The 60 seconds is fixed at launch, not a setting, and it applies mid-round too.
- **Wrong PINs** (FRK-53, tech lead 2026-11-19): After 5 wrong PINs in a row the next try waits 30 seconds, and so on after each further 5. The count and the end of the wait are in secure storage, so a restart does not reset them. Wrong PINs never erase data.
- **No PIN recovery** (FRK-53, tech lead 2026-11-19): A forgotten PIN is fixed by Clear everything, which needs no PIN. Biometrics still unlock if they were turned on.
- **Changing the PIN or turning the lock off needs the current PIN or biometrics** (FRK-53, tech lead 2026-11-19): The lock service does not ask. The settings screens (FRK-65) must.
- **What clear everything removes and keeps** (FRK-53, tech lead 2026-11-19): It removes every key-value entry, every secure item, the encrypted database and every scheduled notification. It keeps the app, permissions given in the phone's settings and store purchases, which Restore purchases brings back. Afterwards the app shows the 18+ confirmation as on first launch.
- **Reinstalls start clean** (FRK-53, tech lead 2026-11-19): iOS keeps Keychain items after a delete, so an install marker in the key-value store is checked at launch, before secure storage is read. A missing marker clears secure storage first and then writes the marker.
- **Backups** (FRK-53, tech lead 2026-11-19): Android app backup is off (FRK-58). On iOS the key-value store may be backed up, and it holds only settings and names. The database is unreadable without its key, which never leaves the device. No further iOS work at launch.
- **The wait doubles** (FRK-53): The ticket said "and so on" after the first 30 seconds. Each further run of 5 wrong PINs doubles the wait (30 s, 1 min, 2 min, 4 min, 8 min) up to a cap of 15 minutes. Doubling slows a guesser more than a steady wait does, and the cap keeps a run of mistakes from locking the owner out for long. The count is a run in a row, so the right PIN starts it again from zero.
- **A try during a wait is ignored** (FRK-53): It is not checked, not counted and does not extend the wait. Even the right PIN is refused until the wait ends. Otherwise the wait would not slow anyone down.
- **Biometrics pass during a wait and reset the count** (FRK-53): The ticket says biometrics still unlock. A pass proves the owner is there, so it also starts the count of wrong PINs again. The phone's own limits on failed biometrics still apply.
- **No phone passcode fallback in the biometrics prompt** (FRK-53): The prompt is made with `disableDeviceFallback` and an empty fallback label, because biometrics are never a way round the PIN. The phone passcode is often a known 4 or 6 digit code.
- **A clock that went backwards locks** (FRK-53): `shouldLock` locks when the time away is negative, because it cannot be trusted. The remaining wait is capped at the longest wait, so a clock set far back cannot lock a player out for good. The clock can still be used to skip a wait by setting it forward. That is accepted, because a monotonic clock does not survive a restart in JavaScript.
- **Turning the lock off also forgets biometrics** (FRK-53): `clearPin` removes the hash, the count and the biometrics choice. Biometrics are an extra on top of a PIN, so turning the lock on again starts with them off.
- **Setting a PIN starts the wrong PIN count again** (FRK-53): A player who sets a new PIN starts clean. Setting one needs the current PIN or biometrics, so this is no way to skip a wait.
- **Checks run one at a time** (FRK-53): The lock service queues checks, so a burst of tries made at once cannot all read the same count and slip past the wait. A test makes five at once.
- **Hash format** (FRK-53): `SHA-256(salt + ":" + PIN)` as 64 lowercase hex characters, with a 16 byte random salt as 32 hex characters, stored as JSON `{ salt, hash }`. Four digits have only 10,000 values, so the hash does not stop someone who can read the secure item. The protection is that the item is readable only on this unlocked phone, plus the wait. This is the tech lead's choice, and the limit is recorded so no one trusts the hash more than it deserves.
- **The service rejects when secure storage cannot be reached** (FRK-53): On iOS a read can fail while the phone is locked. The lock screen (FRK-66) treats a rejection as locked. Only the biometrics calls swallow errors, because a failed prompt just means the player uses the PIN.
- **The Face ID usage text lives in `app.json`** (FRK-53): It is "Use Face ID to unlock Get Freak." The native build reads `app.json` before any JavaScript runs, so it cannot come from `packages/content`. This is an exception to "copy lives in content".
- **The biometrics prompt text is a parameter** (FRK-53): `askForBiometrics(promptMessage)` takes the line from the screen, which reads it from content. The service holds no player-facing text.
- **Screen capture is only added, not used** (FRK-53): `expo-screen-capture` is installed for the lock screen (FRK-66) to hide the app in the app switcher. The permissions for its screenshot listener are blocked, and FRK-66 must unblock them if it needs the listener.
- **A failed clear on a fresh install fails closed** (FRK-53): If the install marker check cannot clear secure storage, or the check times out, the children still mount, because the app is never blocked. The marker stays unwritten, so the check runs again at the next launch. Until then an old PIN hash may still be there. The lock reads it as a lock that is on, so the app asks for a PIN the new owner does not have. That is the safe side. Clear everything needs no PIN and fixes it, and so does the next launch if the clear then works.
