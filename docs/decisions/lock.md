# App lock

- **Off by default** (FRK-53, tech lead 2026-11-19): A player turns the lock on in Settings. Nothing asks at first launch.
- **A 4 digit PIN is required, biometrics are an extra** (FRK-53, tech lead 2026-11-19): Face ID, Touch ID or the phone's fingerprint or face unlock sit on top of the PIN and never replace it. They are offered only when the phone has them set up.
- **The PIN is a salted SHA-256 hash in secure storage** (FRK-53, tech lead 2026-11-19): Readable only while the phone is unlocked and only on this device. It is never in the key-value store and never logged. Whether the lock is on is read from the presence of the hash, so the two cannot disagree.
- **When it locks** (FRK-53, tech lead 2026-11-19): On every cold start, and after 60 seconds or more in the background. The iOS `inactive` state (the notification shade, Control Center, a call banner) and quick trips do not count. The 60 seconds is fixed at launch, not a setting, and it applies mid-round too.
- **Wrong PINs** (FRK-53, tech lead 2026-11-19): After 5 wrong PINs in a row the next try waits 30 seconds, and so on after each further 5. The count and the end of the wait are in secure storage, so a restart does not reset them. Wrong PINs never erase data.
- **No PIN recovery** (FRK-53, tech lead 2026-11-19): A forgotten PIN is fixed by Clear everything, which needs no PIN. Biometrics still unlock if they were turned on.
- **Changing the PIN or turning the lock off needs the current PIN or biometrics** (FRK-53, tech lead 2026-11-19): The lock service does not ask. The settings screens (FRK-65) must.
- **What clear everything removes and keeps** (FRK-53, tech lead 2026-11-19): It removes every key-value entry, every secure item, the encrypted database and every scheduled notification. It keeps the app, permissions given in the phone's settings and store purchases, which Restore purchases brings back. Afterwards the app shows the 18+ confirmation as on first launch.
- **Reinstalls start clean** (FRK-53, tech lead 2026-11-19): iOS keeps Keychain items after a delete, so an install marker in the key-value store is checked at launch, before secure storage is read. A missing marker clears secure storage first and then writes the marker.
- **Backups** (FRK-53, tech lead 2026-11-19): Android app backup is off (FRK-58). On iOS the key-value store may be backed up, and it holds only settings and names. The database is unreadable without its key, which never leaves the device. No further iOS work at launch.
- **The wait doubles** (FRK-53): The ticket said "and so on" after the first 30 seconds. Each further run of 5 wrong PINs doubles the wait (30 s, 1 min, 2 min, 4 min, 8 min) up to a cap of 15 minutes. Doubling slows a guesser more than a steady wait does, and the cap keeps a run of mistakes from locking the owner out for long. The count is a run in a row, so the right PIN starts it again from zero.
- **A try during a wait is ignored** (FRK-53): It is not checked, not counted and does not extend the wait. Even the right PIN is refused until the wait ends. Otherwise the wait would not slow anyone down.
- **Biometrics pass during a wait and reset the count** (FRK-53): The ticket says biometrics still unlock. A pass proves the owner is there, so it also starts the count of wrong PINs again. The phone's own limits on failed biometrics still apply.
- **No phone passcode fallback in the biometrics prompt** (FRK-53): The prompt is made with `disableDeviceFallback` and an empty fallback label, because biometrics are never a way round the PIN. The phone passcode is often a known 4 or 6 digit code.
- **A clock that went backwards locks** (FRK-53): `shouldLock` locks when the time away is negative, because it cannot be trusted. The remaining wait is capped at the longest wait, so a clock set far back cannot lock a player out for good. The clock can still be used to skip a wait by setting it forward. That is accepted, because a monotonic clock does not survive a restart in JavaScript. Time away from the app is a different case and is not left to the wall clock alone: see "The time away is measured on two clocks" (FRK-66). Setting the clock back 59.5 minutes after an hour away made a gap read 30 seconds and opened the app with no PIN, until that fix.
- **Turning the lock off also forgets biometrics** (FRK-53): `clearPin` removes the hash, the count and the biometrics choice. Biometrics are an extra on top of a PIN, so turning the lock on again starts with them off.
- **Setting a PIN starts the wrong PIN count again** (FRK-53): A player who sets a new PIN starts clean. Setting one needs the current PIN or biometrics, so this is no way to skip a wait.
- **Checks run one at a time** (FRK-53): The lock service queues checks, so a burst of tries made at once cannot all read the same count and slip past the wait. A test makes five at once.
- **Hash format** (FRK-53): `SHA-256(salt + ":" + PIN)` as 64 lowercase hex characters, with a 16 byte random salt as 32 hex characters, stored as JSON `{ salt, hash }`. Four digits have only 10,000 values, so the hash does not stop someone who can read the secure item. The protection is that the item is readable only on this unlocked phone, plus the wait. This is the tech lead's choice, and the limit is recorded so no one trusts the hash more than it deserves.
- **The service rejects when secure storage cannot be reached** (FRK-53): On iOS a read can fail while the phone is locked. The lock screen (FRK-66) treats a rejection as locked. Only the biometrics calls swallow errors, because a failed prompt just means the player uses the PIN.
- **The Face ID usage text lives in `app.json`** (FRK-53): It is "Use Face ID to unlock Get Freak." The native build reads `app.json` before any JavaScript runs, so it cannot come from `packages/content`. This is an exception to "copy lives in content".
- **The biometrics prompt text is a parameter** (FRK-53): `askForBiometrics(promptMessage)` takes the line from the screen, which reads it from content. The service holds no player-facing text.
- **Screen capture is only added, not used** (FRK-53): `expo-screen-capture` is installed for the lock screen (FRK-66) to hide the app in the app switcher. The permissions for its screenshot listener are blocked, and FRK-66 must unblock them if it needs the listener.
- **A failed clear on a fresh install fails closed** (FRK-53): If the install marker check cannot clear secure storage, or the check times out, the children still mount, because the app is never blocked. The marker stays unwritten, so the check runs again at the next launch. Until then an old PIN hash may still be there. The lock reads it as a lock that is on, so the app asks for a PIN the new owner does not have. That is the safe side. Clear everything needs no PIN and fixes it, and so does the next launch if the clear then works.
- **One route for turning the lock on and for its settings** (FRK-65): Frames 6 and 8 both start from the App lock row, one for a lock that is off and one for a lock that is on. `/app-lock` is one route that reads the lock when it opens and shows the turn on flow or the lock's settings. Settings has one row and no screen has to guess which of two routes to push.
- **The row reads the lock each time Settings is in view** (FRK-65): `AppLockRow` reads on focus, so it is right after the lock screens close, with no event between screens. It shows no value until the first read, or when the read fails, because a guessed "Off" for a lock that is on would be wrong.
- **Biometrics availability names every kind** (FRK-65): `getBiometricsAvailability` gains `kinds`, the list of everything the phone has. The design names Android biometrics by kind only when the phone has one kind, and uses the general "phone unlock" words for any other phone, which `kind` alone cannot tell. `kind` is unchanged, so FRK-53's tests and callers hold.
- **Naming the biometrics** (FRK-65): iOS, face is Face ID and a fingerprint is Touch ID. Android, a single fingerprint is "fingerprint", a single face is "face unlock", and anything else (both, or an iris reader) is "phone unlock". When the phone has none set up there is no kind, so the disabled switch uses the "phone unlock" words, whose reason reads "This phone has no fingerprint or face unlock set up." The design draws the Face ID reason as an example for iOS, and that needs a kind the service cannot give for a phone with nothing set up.
- **The app mark is left off the biometrics offer and the done screen** (FRK-65): Frames 6 and 7 draw the app mark image (`splash-mark-1024.png`) above the text. FRK-19 adds that file and it is not on main, so the screens hold the same text and buttons in the same places without it. A later change drops the image in.
- **The tries left line is left to the lock screen** (FRK-65): Frame 9 draws "2 more tries before a short wait" from the third wrong PIN. The lock service does not give the count of wrong PINs, and frame 8 draws only "Wrong PIN. Try again." for the current PIN step, so this ticket shows that line and the wait countdown. FRK-66 adds the count to the service if it builds the line.
- **No error haptic from the PIN pad** (FRK-65): The design says the error haptic plays when Vibration is on. The feedback module has no error moment, and adding one needs its own sound file and haptic pattern, which is not a keypad's job. The pad shakes and announces the error. A feedback moment can be added later and called from `PinPad`.
- **Failures the design does not draw** (FRK-65): The PIN not saving (secure storage out of reach), the biometrics switch failing its check, and the lock not turning off each need a line. They use `copy.lock.saveFailed` ("That did not save. Try again.") and `copy.biometrics.toggleFailed` ("That did not work, so it stays off."), shown in the same danger style as the other error lines. The offer's own failure line says "or choose Not now", which the switch has no equivalent of, so the switch has its own.
- **Wrong current PINs are checked by the lock service** (FRK-65): `VerifyPinStep` calls `checkPin`, so a wrong PIN counts toward the wait with no second count in the screen. A wait that is already running, even from before a restart, shows when the step opens, as a disabled keypad and the countdown. The right PIN is refused during a wait, as on the lock screen.
- **Biometrics unlock the current PIN step only when they are on** (FRK-65): The "Use Face ID" link under the keypad shows only when the player turned biometrics on and the phone still has them set up. The prompt reads "Unlock to continue", the lock screen's text, because the player is proving who they are in the same way.
- **The first PIN is forgotten after a mismatch** (FRK-65): The first step starts again with empty dots, and the old first PIN is not compared with the next one. Header back from the second step also forgets it. The digits are held only in the step's state while it is on screen.
- **The fourth dot is held for 150 ms** (FRK-65): As the design says, so it is seen before the step moves on. The keypad ignores Delete and more digits during the hold, and a step that is left during the hold never submits.
- **"PIN changed" and "App lock is off" are announced, not shown** (FRK-65): The design says they are announced, and draws no visible line for either. Changing the PIN returns to the lock's settings. Turning the lock off leaves for Settings, where the row reads Off.
- **A stored biometrics choice with no biometrics set up** (FRK-65): The switch shows off and disabled, and the row reads "On, PIN", because the lock cannot use them. The stored choice is left as it is, so setting the phone's biometrics up again brings the switch back to on without a new prompt.
- **A lock that turned off while a step was open** (FRK-65): If the check answers that the lock is off, the step lets the player go on, because there is no PIN left to protect.
- **Screen tests run the real lock service** (FRK-65): `lock/testing/createTestLock` is the real `createLockService` over in-memory secure storage, a Node SHA-256 and a stand-in phone, with the clock on `Date.now`. A test that types five wrong PINs sees the real wait, and one that turns the lock off sees the real hash and choice removed. Only the biometrics prompt and the secure storage are faked.
- **The lock service reaches screens through a context** (FRK-65): `useLockService()` gives the real service by default, so the app needs no provider and FRK-66 can use it the same way. A test puts a fake above a screen with `LockServiceContext.Provider`.
- **Back from choosing a PIN returns to the explainer** (FRK-65): Frame 6 draws a back control on the first PIN step and says only that back from the second step returns to the first. The first step goes back to the explainer, so a player who changed their mind can read it again or leave from it.
- **Leaving the app forgets what was typed and what was proved** (FRK-65, review): `useClearOnBackground` listens for the `background` and `inactive` app states. `PinEntryStep` clears its numbers and drops a held last number, `ChoosePinSteps` returns to the first step and forgets the first PIN, and `LockOnSettings` returns to its status and forgets that the current PIN was typed, so Change PIN asks again on return.
- **The phone's biometrics prompt is not leaving the app** (FRK-65, review): iOS reports `inactive` while the Face ID prompt is up. The two places that show the prompt on these screens run it inside `whileBiometricsPromptIsOpen`, and the hook ignores changes while one is open. Without that, a passed Face ID check would land on a screen that had just been reset.
- **One answer at a time** (FRK-65, review): `PinEntryStep` sets an in-flight flag in a ref the moment the last number is typed, so two presses in one frame submit once and count one wrong PIN. The biometrics link has its own in-flight flag. `LockOnSettings` accepts one verification, runs Turn off once and leaves once, so `router.back` cannot run twice and pop past Settings.
- **Turning off removes the hash last** (FRK-65, review): `clearPin` removes the biometrics choice, then the wrong PIN count, then the hash, one after another and not together. If a remove fails the hash is still there, so the lock stays on and the PIN still works, and nothing is left half turned off.
- **The lock test helpers cannot reach the app** (FRK-65, review): `lock/testingHelpersStayInTests.node.test.ts` scans the sources and fails if a file that is not a test, and not in `lock/testing`, imports from `lock/testing`.
- **Focus does not move when a step changes** (FRK-65, review): The design says focus returns to the screen underneath only for the lock screen's fade out. Steps here replace each other under the same heading role, and moving the screen reader focus to the new heading is left as a later accessibility pass.
- **The lock screen is a native `Modal`, with a cover in the tree under it** (FRK-66): The ticket says an overlay above the navigator and not a route, and a `Modal` is that. A plain view would sit under any dialog the app had open (the end round dialog, the Not this one sheet with card text), which would stay readable and pressable over the lock, and a pressed Clear everything there would need no PIN. A native `Modal` sits above them, takes the screen reader's focus and gives the Android back button to `onRequestClose`. The `PrivacyCover` in the tree is there because the modal can take a frame or two to appear. A hardware back listener that takes the press covers the time before it shows.
- **No screen shows before the lock screen on a cold start** (FRK-66): `LockGate` mounts the app only after the first read of whether the lock is on has answered, and shows the cover until then. A read that rejects counts as locked, as FRK-53 says. The app stays mounted for good after that, so a lock and an unlock never remount it.
- **Coming back after 60 seconds covers first and then reads the lock** (FRK-66): The gate goes to `checking`, with the cover up and the app hidden, and settles when the lock has been read. A player with the lock off sees the cover for the length of one secure storage read each time they come back after a minute. The other order, showing the app until the read answers, would show the app for that moment to a player with the lock on.
- **A lock screen that is already up is left alone** (FRK-66): If the app comes back after more than a minute while the lock screen is showing, nothing restarts, so the phone prompt does not show a second time. The prompt shows once each time the lock screen appears, which is each time the gate goes from unlocked to locked.
- **Only `inactive` is ignored while the phone prompt is up** (FRK-66): iOS reports `inactive` while Face ID shows, and that is neither the privacy cover nor the start of time away. A `background` during the prompt still starts the time away, because the player really left.
- **Screen capture and the cover follow the lock, and are not used until it is read** (FRK-66): Android sets `FLAG_SECURE` and iOS shows the cover only while the lock is on. Until the first read answers, neither is changed, so a player with the lock off is never blocked from a screenshot. `LockService` gains `subscribe`, called when a PIN is set or cleared, so the gate reads again when the lock is turned on or off in Settings. Without it, turning the lock on and pressing home at once would leave the first thumbnail unprotected.
- **Android only for `FLAG_SECURE`** (FRK-66): The ticket's decision. iOS has no such flag and uses the cover. `preventScreenCaptureAsync` is not called on iOS. The screenshot listener of `expo-screen-capture` is not used, so its blocked Android permission in `app.json` stays blocked.
- **The wrong PIN result carries the tries left** (FRK-66): FRK-65 left the tries left line to this ticket and said the service would need to give the count. `checkPin` returns `{ status: 'wrong', triesLeftBeforeWait }`, from `triesLeftBeforeWait` in the core, which counts down from 5 through each run of 5. The lock screen shows the design's line from the third wrong PIN (2 more tries, then 1 more try). It does not show it on a screen that opens with 3 wrong PINs already stored, because only a try gives the count.
- **A line for a PIN that cannot be checked** (FRK-66): The design draws no state for secure storage being out of reach. The lock screen says "Could not check your PIN. Try again." and stays locked, because `checkPin` rejects in that case. The PIN step's own "That did not save" line would be wrong here. Forgot PIN is still there. A correct PIN whose wrong PIN count cannot be removed also rejects, so the player is not let in until storage answers.
- **The fade is the modal's, not 150 ms** (FRK-66): The design says the overlay fades out over 150 ms, with no fade when Reduce Motion is on. `Modal` has no duration, so the system fade is used, and none at all when Reduce Motion is on. The lock screen also fades in, which the design does not draw, and the cover under it hides the app while it does. To be checked on a device.
- **Focus after unlocking is left to the system** (FRK-66): The design says focus returns to the screen underneath. Dismissing the modal gives it back on both platforms, and no focus call is made. To be checked with VoiceOver and TalkBack.
- **The privacy cover shows the mark at 200 dp** (FRK-66): The design draws the mark at 120 in the app switcher card. That card is a scaled down screen, and the splash mark is 200 on a full one, so the real cover uses 200 to match the splash.
- **The app mark is added** (FRK-66): `assets/images/splash-mark-1024.png`, the file the design names, is copied from the brand folder. FRK-19 adds the same file at the same path, so the two should merge without a conflict. The native splash still shows the older mark until FRK-19 lands. `AppMark` is in `features/lock` and the FRK-65 screens can use it in place of the gap noted above.
- **The Face ID usage text is not changed** (FRK-66): The design suggests "Unlock the app with Face ID." in place of FRK-53's "Use Face ID to unlock Get Freak." It lives in `app.json`, and changing it changes the native fingerprint and needs a new build, which this ticket may not cause. It is left as it is for the owner to decide.
- **The lock screen reuses the PIN step with a hero** (FRK-66): `PinEntryStep` takes either a header or a `hero`, which replaces the header and puts the hero above the dots, as frame 9 draws. The hold on the fourth dot, the in-flight guard and the clearing on leaving the app are all the step's own.
- **The default lock clock is read each time** (FRK-66): `defaultLockService` passes `() => Date.now()` and not `Date.now`, so a test that replaces the clock moves the lock's clock as well. Without it a route test could not show the wait ending.
- **Route tests start unlocked unless they are about the lock** (FRK-66): The real root layout now has the lock gate, so a test with a PIN stored starts locked. `launchUnlockedApp` in `features/welcome/testing` types the test PIN if the lock screen is up. `lock/testingHelpersStayInTests` now also allows `features/welcome/testing/` to import the lock's test helpers, and the release bundle check confirms none of them ship.
- **The time away is measured on two clocks** (FRK-66, security review): The gate stamps both `Date.now()` and `performance.now()` when the app reaches the background. On return it locks if either `shouldLock` check says 60 seconds or more, and the wall clock check keeps the core's lock for a clock that went backwards. A person who sets the phone clock back during a long trip can no longer make it look short, because the steady clock still counts it. The steady clock can pause while the phone sleeps, which would make a trip look short, so the wall clock is the other half. Either one says lock, and forging both at once is not possible from the phone's settings. The window before this fix was a clock set back by nearly the whole trip. A restart always locks.
- **Reads of whether the lock is on are newest wins** (FRK-66, security review): The first read, the read on return and the read after a change each carry a number, and only the newest may set whether the lock is on. Two reads that answer out of order, such as a quick on and off in Settings, can no longer leave the cover or `FLAG_SECURE` in the wrong state.
- **Clear everything removes secure storage last** (FRK-66, security review): The order is notifications, then the database and the key-value store, then secure storage, and secure storage is skipped when an earlier step failed. A Forgot PIN wipe that fails part way now leaves the PIN hash and the lock on, and not a lock that is quietly off over data that is still there. A failed wipe can be tried again, and the retry runs every step. The database key stays until the end, which is safe because the database file is deleted first.
- **Known device checks for the privacy cover** (FRK-66, security review): Three things cannot be shown by tests and need a phone. First, on iOS the cover is drawn by JavaScript when the app goes inactive, so it races the system's snapshot for the app switcher card. Second, on Android each React Native `Modal` is its own window and `FLAG_SECURE` is set on the activity window, so the recents thumbnail with a dialog open may show that dialog. Third, nested modals (the Forgot PIN dialog inside the lock modal) need a look on both platforms. No more machinery is built for these now. If a device shows a leak, the next step is a native cover or setting the flag on each modal window.
- **The gate keeps `=== true` for the cover** (FRK-66, security review): Before the first read the phase is `checking`, which is already covered, so a cover that waits for `isLockOn` to be true and one that waits for it not to be false behave the same in every state the gate can reach. The test for the first read covers the real behaviour.
