# Privacy

- **Error reporting and analytics** (FRK-56): None at launch. No SDK for either in the app. Crash data comes only from what Apple and Google collect from players who opt in.
- **Encryption export answer** (FRK-56): `ITSAppUsesNonExemptEncryption` is `YES` now that SQLCipher ships (FRK-41), as an industry standard algorithm not provided by the operating system. The owner files the French declaration or leaves France out of the launch countries. FRK-58 sets the flag in the iOS config. `docs/compliance.md` gives the reasons.
- **No error reporting or analytics SDK** (FRK-58): None ships, as the compliance review requires. The only network call is the update check.
- **Export compliance flag** (FRK-58): `ITSAppUsesNonExemptEncryption` is `true`, set in `ios.infoPlist`, as `docs/compliance.md` concludes now that SQLCipher ships. The owner files the French declaration or leaves France out.
- **No push** (FRK-53): `expo-notifications` is added for local notifications only. The app never requests a push token, so the privacy answers do not change. The library bundles Firebase Messaging on Android, which stays idle without a `google-services.json`. Verify with the network monitor check in FRK-74.
- **The notifications plugin is not listed in `app.json`** (FRK-53): It gets no options, so listing it would add nothing. Expo applies it anyway when the package is installed, which puts `aps-environment` in the iOS entitlements. EAS sets the value for the build, and a store build that does not use push is fine with it. Check on the first iOS build.
- **Privacy manifest union unchanged** (FRK-53): `expo-notifications` ships a manifest that declares the user defaults reason `CA92.1`, which `privacyManifests` already holds. `expo-local-authentication` and `expo-screen-capture` ship none. The `toEqual` test in `appConfig.test.ts` still holds.
- **No PIN, hash, salt or key in logs or errors** (FRK-53): The secure storage, install marker, clear everything and lock tests spy on the console, and the lock service never puts a PIN in an error. The clear everything result holds no error message.
- **Sentry error reporting is added** (FRK-83): The owner decided on 2026-11-19 that the app gets Sentry. This replaces the earlier entries that say no error reporting SDK ships. Analytics is still not added.
- **Reports are scrubbed by allowlist in the app** (FRK-83): Every message is removed, because an error message can quote a card, a name or a typed dare. The user, the request, extra data, unlisted tags and unlisted contexts are removed too. The error type, the stack, the release and the route names stay.
- **The route trail is the app's own** (FRK-83): Sentry's navigation integration is not used. `RouteTrail` records Expo Router's segments, so a dynamic part of a route stays as its placeholder and no id from an address is sent.
- **No `Sentry.wrap` on the root layout** (FRK-83): It adds touch tracking and performance spans, and neither is sent. Unhandled errors are caught without it, and render errors are reported by `CrashBoundary`.
- **Reports the native side sends are not scrubbed in the app** (FRK-83): A crash in native code, an Android "app not responding" report and an iOS app hang are sent by the native SDK and never reach `beforeSend`. They hold no text from the app's screens, but they keep the native error's own message. The privacy policy says so.
- **Every phone gets the same fixed user** (FRK-83): With no user set, the native SDKs on both platforms fill in an id made once for each install. `initMonitoring` sets the user to the fixed word `player`, which stops that. Reports from JavaScript have the user removed anyway.
- **Each context is an allowlist of keys** (FRK-83): The SDK merges the native device context into every report, and on Android it holds the install id as `device.id`, with the boot time, time zone and locale. The device context keeps only what describes the kind of phone.
- **The install id on Android native reports is removed in Sentry, not in the app** (FRK-83): A native report still holds `contexts.device.id`, and nothing in the app can take it off. The runbook gives an advanced data scrubbing rule for the project. Until the owner adds it, a native report from Android can be tied to one install, and the privacy policy says a random number can be included.
- **Native tap breadcrumbs are off on Android** (FRK-83): A small config plugin sets `io.sentry.breadcrumbs.user-interaction` to false. They hold a view's class and id, not its text, but the ticket says no tap breadcrumbs.
- **The crash boundary is per screen** (FRK-83): It sits in the root navigator's `screenLayout`, so the navigator stays mounted when a screen fails and "Start again" can leave for the first screen. A boundary above the navigator rebuilds it from the address the app was opened at, which loops when that screen is the one failing.
- **The test error works on the live channel** (FRK-83): The owner decided on 2026-11-19 that the project has no preview stage, so the link that throws a test error works on the `production` channel, and on `preview` until FRK-84 retires it. It will be in the store build, where it shows the crash screen and sends one test report. Whether to keep, hide or remove it before the store release is a question for the owner in FRK-84. A development build never reports, so the link does nothing there.
- **The release of a build's own JavaScript is the runtime version, not the commit** (FRK-83): Only the README's update command sets `EXPO_PUBLIC_COMMIT_SHA`. Putting the commit into a build would change the config for every commit, and its effect on the fingerprint was not checked. An update names its commit.
- **No opt-out switch for crash reports yet** (FRK-83): The ticket leaves it to the owner. None is built. If the owner wants one, it is a settings switch that `initMonitoring` reads before it starts the SDK.
- **Development and preview builds skip the source map upload** (FRK-83): The Sentry build step fails a build that has no auth token. Those two profiles set `SENTRY_DISABLE_AUTO_UPLOAD`, so they build without one. A `production` build uploads and needs `SENTRY_AUTH_TOKEN` in the build service.
- **The DSN is read from `EXPO_PUBLIC_SENTRY_DSN`** (FRK-83): It is an environment variable of the build service and is in no committed file. A build without it sends nothing. The runbook sets it for `production` and `preview`, so the build on the owner's phone reports too. A development build never reports.

- **What a notification may contain** (FRK-68): Only the body line, the iOS hidden preview placeholder and the Android channel name and description, all in `copy.notification`. They name no game, card, category, level, drink or player and say nothing of what the app is for, a test checks them against the names in `packages/content`, and there is no title, badge or data payload. The sound is the system default.
- **The reminder is a local notification only** (FRK-68): It is scheduled on the phone. The app still never requests a push token, and Clear everything cancels it, so the privacy policy and store answers do not change. Turning it on is the only time the app asks for notification permission.
- **iOS shows the app's name** (FRK-68): A notification on iOS always carries the app's icon and name, and the lock screen cannot be hidden per app. The reminder screen says so, and the placeholder replaces the words when previews are hidden. On Android the channel keeps the reminder off the lock screen.
