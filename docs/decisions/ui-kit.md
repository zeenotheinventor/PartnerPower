# UI kit

- **Role and name for the screen shell** (FRK-4): The shell is a layout container with no role or name of its own. A label on a container that is not an accessibility element does nothing on iOS. The "role and name" criterion is applied to components that mean something by themselves.
- **Depth edge** (FRK-4): Built from layered views in token colours. Token-coloured shadows do not exist.
- **Settings screen captions** (FRK-26): The kit `Toggle` has an optional `description`, drawn under the label and given as the switch's accessibility hint. The settings rows use it.
- **FavouriteToggle is named by a prop** (FRK-55): The kit holds no copy, so `FavouriteToggle` takes its name as a `label` prop and the summary passes `copy.favourite.label`. The architecture rule outranks the design's note that the name comes "from content", which the prop still satisfies, since the caller reads it from there.
- **Locked `Toggle` look** (FRK-60): The track gains a foreground border with smaller padding, so it is the same size. The row is not dimmed, as with `CategoryToggle`.
- **Characters are code-drawn vector art** (FRK-18): The cast is drawn by us as vector art in code, rendered with `react-native-svg` and animated with Reanimated, instead of Rive files from an illustrator. Decided by the owner on 2026-11-19, so the cast ships without waiting on an illustrator.
- **Neutral role ids for the cast** (FRK-18): `host`, `dealer`, `hype`, `gatekeeper` and `shy`, because a display name changed twice. Names and personality lines are in `characterNames` in `content`. The id type is in `core`, which `content` may import.
- **Animated views, not animated SVG groups** (FRK-18): Each moving part is a full-size `Svg` layer in a Reanimated `View`. react-native-svg converts `transform` to a matrix in JavaScript, so a transform on an SVG group from the UI thread is unreliable. A `View` transform is known to work.
- **Reanimated animated styles may be inline** (FRK-18): An animated view takes its style through the `style` prop and `StyleSheet.absoluteFill`, because Reanimated writes it on the UI thread. Everything else keeps to classes.
- **Mood moves with the character** (FRK-18): A mood a character cannot show is a compile error. The `Character` props are a union over the roles, so the role and the mood are checked as a pair. At runtime an unknown mood falls back to idle instead of throwing.
- **Character art is data, not screen code** (FRK-18): The art is plain data files in `apps/mobile/characters`, one per character, with the layer order in one `composeLayers` that the component and the preview script share.
- **Reanimated under Jest, one shared mock** (FRK-18): Reanimated's official mock is registered as one shared module object, with `useReducedMotion` and `withRepeat` as `jest.fn`, because the router's testing library registers its own mock of the same module. A resolver loads the plain JavaScript worklets only for Reanimated and worklets, because a broader one broke packages whose pnpm path names the worklets as a peer.
- **Face down card in the kit** (FRK-49): `Card` takes `faceDown`, `mark`, `title` and `label`, a third branch of its props with no children. It is one `img` named by its label, so the mark and title are not read twice. It is in the kit gallery.
- **Countdown holds no copy and no haptic** (FRK-50): It takes `label`, `secondsText` and `endText` as props, as `FavouriteToggle` does, and tells the caller when it ends with `onEnd`, so the caller plays the haptic. The vibration card reuses it.
- **Countdown stops its timeout out of the foreground** (FRK-50): The design refreshes the digits when the app returns to active. It also drops the pending timeout when the app leaves active, so nothing ticks, announces or fires `onEnd` or a haptic while the app is not on screen. Coming back works the time left out from the clock and fires `onEnd` then if the time ran out.
- **Countdown bar fill is an absolute view** (FRK-50): The fill is a full size `Animated.View` laid over the track with `StyleSheet.absoluteFill`, with the token coloured view inside it, so the animated style carries only the `translateX`. This follows the character art decision about animated views, and it avoids a class name on an animated component.
- **Countdown idle shows the given seconds** (FRK-50): Before it starts, the digits are the full `seconds` whatever an earlier run left, so a stopped and reset countdown reads as new.
- **Gallery entry** (FRK-50): The gallery shows an idle countdown, a live one with a button that starts it from ten seconds again, and one that has ended. The running state is the live one.
- **Dialog is the end round dialog, made general** (FRK-54): `Dialog` takes `visible`, `title`, `body`, `confirmLabel`, `cancelLabel`, `onConfirm` and `onCancel`. It has the end round dialog's look and a transparent `Modal`. The panel has role `alertdialog`, the title as its label, and `accessibilityViewIsModal`. It is not one accessibility element, because that would hide its buttons on iOS, so a test finds it by its label and checks the role. `EndRoundDialog` is left as it is until the play screen tickets have merged.
- **TextField speaks its error and count with the field** (FRK-54): The error and the count under the box are hidden from a screen reader, and the input's hint is the error, then the count in words. The words come from the caller as `countHint`, because the kit holds no copy. The hint joins them with a space, not a full stop, because the error is a sentence already. The caller announces a new error with `AccessibilityInfo`.
- **The accent colour carries an error** (FRK-54): An error, or a count over the maximum, takes the accent border, and the message is in the foreground colour with an accent "!" badge, as the design draws it. There is no error colour token. The border is the foreground colour while the field has focus, and an error wins over it.
- **Screen has an optional footer** (FRK-54): `footer` is pinned under the content, outside a scroll view, inside the keyboard avoiding view, on a border line over the background colour.
- **The test safelist gains `mr`** (FRK-54): The setup row's chevron uses a right margin, and a prefix missing from the safelist silently does not resolve in a component test.
- **The Dialog panel is not an accessibility element, so no `alertdialog` role query** (FRK-54): The design note says to test it with `getByRole('alertdialog', { name })`. That query only reaches an accessibility element, and making the panel one would group its children into a single element on iOS and hide the confirm and cancel buttons. So the panel keeps `role="alertdialog"`, its title as label and `accessibilityViewIsModal`, and tests find it by label and check the role prop.
- **The character count line is a shared copy key** (FRK-54): `copy.ui.characterCount` ("{count} of {max} characters") is the spoken count for `TextField`'s `countHint`. It sits under `ui` rather than `ownCards` so the deck editor reuses it.
- **The kit `Dialog` is extended, not duplicated** (FRK-63): Clear everything needs a content slot, an error line, a danger confirm and a busy state, so `Dialog` gains `children`, `error`, `confirmVariant` (`primary` or `danger`) and `busy`. Every existing caller is unchanged because each prop is optional. A second dialog would have split the one the end round and delete dialogs share.
- **Dialog long content uses the overlay padding, not a measured height** (FRK-63): The design says the scroll area stops at the window less 160. The overlay keeps 80 above and below (`py-[80px]`), the panel is `max-h-full`, and the scroll area shrinks, so the same result needs no window height read at run time and no `style`. The 80 is an arbitrary value because the spacing scale stops at 64.
- **Dialog error line** (FRK-63): `role="alert"` in the danger colour, with a polite live region, and announced when it appears because iOS does not read live regions. It sits outside the scroll area so it is always in view.
- **Dialog back button while busy** (FRK-63): While `busy`, `onRequestClose` is a function that does nothing, so Android back is ignored during a clear. It is not left out, because Android expects a handler on a Modal.
- **`SettingsRow` highlight is the inner face** (FRK-63): The pressable carries `group` and `-mx-8`, and the face inside carries `px-8` and `group-active:bg-background`. A highlight on the pressable itself did not update under test, and the face pattern is the one `Button` uses.
- **`SettingsRow` name** (FRK-63): The accessible name is `label, value` and the caption is the hint, so a value is read once. The row is a `button`, and a test finds it by that name, for example `App lock, On, PIN`.
- **Gallery entries** (FRK-63): The kit gallery shows the danger button, the four kinds of `SettingsRow`, and a second dialog with a list, an error line and a danger confirm.
- **Dialog buttons are found inside the dialog in tests** (FRK-63): The Clear everything row and the dialog's confirm button share a name, as the design's copy gives them. A test finds the dialog's buttons with `within(getByLabelText(title))`. On a phone the modal hides the row from a screen reader, so the shared name does not confuse anyone.
- **`PinPad` has no `length` prop** (FRK-65): The design lists `length` (4) as a prop. The PIN is always the core rule `pinLength`, so a second source of the number could only disagree with it. The dots line is the copy "{count} of {length} digits entered", filled from that constant.
- **The pad is controlled and holds no digits** (FRK-65): The screen passes `value`, `onChange` and `onComplete`, so the digits live only in the state of the screen that is on screen and the pad never keeps them. It has no text field, so the phone keyboard and autofill never see the PIN.
- **Keys are not `Button`s** (FRK-65): The design gives a key the secondary button's look with a `type-title` label and `py-12`, where `Button` fixes `type-heading` and `py-16`. Adding a size to `Button` for one caller was more than building the key from the same pieces (a depth edge, a face that sinks onto it). Delete is a plain pressable with no face, as drawn.
- **The error is announced by the pad, the countdown by the screen** (FRK-65): The pad calls `announceForAccessibility` when `error` appears, because iOS has no live regions. A screen must clear the error when the player types again so the same error is announced as new. `message` is not announced by the pad, because a countdown changes each second and the screen announces it at the start and every 10 seconds.
- **The shake is an animated value** (FRK-65): Like the toast's fade, a transform driven by `Animated` cannot be a class, so the dots wrapper has the one `style` with `translateX`. It runs 0, -4, 4, -4, 4, 0 over 240 ms, and not at all with reduce motion on, which it reads from the phone when an error appears.
- **The message slot is 44 high, as an arbitrary value** (FRK-65): The design gives the line slot `min-h-44` so the keypad never jumps. 44 is not on the spacing scale, so it is `min-h-[44px]`, with `max-w-[300px]` for the line's width, as one-off values.
- **Gallery entries** (FRK-65): The kit gallery shows the pad to try (the fourth digit shows a sample error and clears the dots), partly filled, full, with an error, and waiting with a disabled keypad and a message.
